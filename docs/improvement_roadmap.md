# dFBA-RL システム改善指針

## 現状の問題分析

### 1. 主要な問題点

1. **エピソード長が1で即終了**
   - ゴム分解が全く進んでいない（0.00%）
   - 環境が1ステップで終了している
   - 学習が全く進まない状態

2. **GPU使用の非効率性**
   - MlpPolicyでGPU使用は推奨されない
   - dFBAシミュレーション（CPU処理）がボトルネック
   - GPU-CPU間のデータ転送オーバーヘッドが発生

3. **報酬が一定**
   - 全エピソードで報酬=186.74（変動なし）
   - 学習が進んでいない証拠

### 2. ボトルネックの特定

**計算時間の内訳（推定）:**
- dFBAシミュレーション（FBA×3種）: **95-99%**
- PPO推論・学習: **1-5%**

→ **PPOをGPU化しても全体の高速化効果はほぼゼロ**

---

## 短期的改善策（即座に実装可能）

### Phase 1: CPU最適化とデバッグ強化

#### 目標
- エピソード長を10以上に延長
- ゴム分解率を1%以上達成
- 学習の進行を確認

#### 実装内容

1. **CPUモードへの切り替え**
   - `src/ppo_agent.py`: `device='cpu'`をデフォルト化
   - GPU警告の解消

2. **環境終了条件の緩和**
   - `src/rl_environment.py`: バイオマス全滅閾値を0.01→0.001に変更
   - より長いエピソードを許容

3. **デバッグ出力の追加**
   - ゴム分解の詳細ログ
   - 各ステップのバイオマス・代謝物濃度
   - FBA成功/失敗の追跡

4. **ゴム分解速度の検証**
   - 現在の分解速度が適切か確認
   - 必要に応じて調整

#### 期待される効果
- エピソード長: 1 → 10-50
- ゴム分解率: 0% → 5-20%
- 学習時間: 変化なし（CPU最適化のため）

## 中期的改善策（1-2週間で実装）

### Phase 2: シミュレーション高速化

#### 目標
- dFBA計算時間を50%削減
- 並列環境で学習速度を3-5倍向上

#### 実装内容

1. **FBAソルバーの最適化**
   ```python
   # COBRApyのソルバー設定最適化
   model.solver = 'glpk'  # または 'cplex', 'gurobi'
   model.solver.configuration.tolerances.feasibility = 1e-6
   model.solver.configuration.presolve = True
   ```

2. **並列環境の導入**
   ```python
   from stable_baselines3.common.vec_env import SubprocVecEnv
   
   # 4並列環境
   env = SubprocVecEnv([make_env() for _ in range(4)])
   ```

3. **タイムステップの最適化**
   - 現在: dt=0.5h
   - 提案: dt=1.0h（精度とのトレードオフ）

4. **代謝物数の削減**
   - 現在: 45種の代謝物
   - 提案: 主要な10-15種に絞る

#### 期待される効果
- 1エピソードの計算時間: 50%削減
- 並列化による学習速度: 3-5倍向上
- 総学習時間: 10000ステップが数分→数十秒

## 長期的改善策（1-3ヶ月で実装）

### Phase 3: サロゲートモデルによる根本的高速化

#### 目標
- dFBA計算を機械学習モデルで置き換え
- GPU活用による100-1000倍の高速化
- リアルタイム学習の実現

#### 実装内容

1. **FBAサロゲートモデルの訓練**
   ```python
   # ニューラルネットワークでFBAを近似
   class FBASurrogate(nn.Module):
       def __init__(self, n_metabolites, n_reactions):
           super().__init__()
           self.net = nn.Sequential(
               nn.Linear(n_metabolites, 256),
               nn.ReLU(),
               nn.Linear(256, 256),
               nn.ReLU(),
               nn.Linear(256, n_reactions)
           )
       
       def forward(self, metabolite_concentrations):
           return self.net(metabolite_concentrations)
   ```

2. **データ収集パイプライン**
   - 多様な条件でFBAを実行
   - (代謝物濃度, フラックス分布)のペアを収集
   - 10万-100万サンプルを生成

3. **サロゲートモデルの統合**
   ```python
   class FastdFBASimulator:
       def __init__(self, surrogate_models):
           self.surrogates = surrogate_models  # GPU上
       
       def step(self, state):
           # FBAの代わりにニューラルネット推論
           fluxes = self.surrogates(state.metabolites)
           # 以降は通常のdFBAと同じ
   ```

4. **GPU上での完全な学習ループ**
   - 環境（サロゲート）: GPU
   - PPO: GPU
   - データ転送ゼロ

#### 期待される効果
- 1ステップの計算時間: 100-1000倍高速化
- 学習時間: 数時間→数分
- リアルタイム制御の実現

## リスクと対策

### リスク1: サロゲートモデルの精度不足
**対策:**
- 物理制約（質量保存則）を損失関数に組み込む
- ハイブリッドアプローチ（重要な反応のみFBA、他はサロゲート）

### リスク2: 並列環境でのメモリ不足
**対策:**
- プロセス数を動的に調整
- 軽量なモデル（代謝物数削減）を使用

### リスク3: 学習が収束しない
**対策:**
- 報酬関数の再設計
- カリキュラム学習（簡単なタスクから段階的に）
- ハイパーパラメータの最適化
