# AMNガイド付き高速化と状態遷移拡張：20260904イテレーション統合報告

本統合文書は、AMN（Amortized Neural Network）アプローチを参考にしたGPU加速dFBA/LPソルバーの高速化計画と、その後の状態遷移カバレッジ拡張・GPU修復計画の2件の関連ドキュメント（`AMN_GUIDED_ACCELERATION_PLAN_20260904.md`および`AMN_TRANSITION_SCALING_20260904.md`）を統合したものです。計画段階から測定結果・限界までの一連の進捗を時系列順に整理し、数値・結論を原文通りに転記しています。**最終的な結論**: 合成データルーティングから実軌跡学習へ移行し、状態遷移カバレッジを拡大したものの、開発環境における第二段階交換LPにおいて未解決の問題が残り、完全な2ステップ/120ステップのGPU高速化は未確立であり、PPO学習や完全デバイス常駐dFBAの主張は行われていません。

## 1. AMNを参考にした高速化計画（初期計画とパイロット実装）

（出典: `AMN_GUIDED_ACCELERATION_PLAN_20260904.md`, 2026-09-04）

### 1.1 背景と参照

- **参照**: Faure et al., *Nature Communications* 14, 4669 (2023), [論文](https://www.nature.com/articles/s41467-023-40380-0), [著者実装](https://github.com/brsynth/amn_release) (MITライセンス)
- **論文の主張**: ニューラル層が初期フラックスを予測し、LP/QPまたはWtのメカニスティック反復を事後実行する。これは初期推定の償却（amortization）を動機付けるものであり、GEMサロゲートが自動的にCPU LPに勝ることを主張するものではない。
- **注意**: AMN-QPフィッティングとLP成長最適化は異なるタスクであり、表現型回帰は、私たちの3段階コミュニティ最適化や120ステップdFBA軌跡の証明にはならない。

### 1.2 適合戦略（AMNの再現ではなく適応）

1. **コンパイル済みLP基底のニューラル提案**: オフラインLPパラメータから、コンパクトなニューラルネットワークで開始基底を学習。メカニズム層がその基底からフラックスを再構築し、元の完全LPを保証。**ニューラル信頼度のみではフラックスを受け入れない**。
2. **拒否時の処理**: 既存の網羅的銀行とGPU修復パスを保持。許容誤差の緩和、生物学的範囲の変更、オンラインCPU LP呼び出しは行わない。
3. **訓練データ**: 有償オフラインデータまたは宣言されたオフラインアンカーの摂動のみを使用。評価用シードや失敗した評価LPは訓練データに含めない。
4. **比較評価**: ニューラルルーティングと非ルーティングを、マッチした独立環境で比較（転送・ディスパッチを含む）。コールド/準備時間、受理/修復割合、総CPU LP呼び出し回数、完全エンドポイント精度を報告。
5. **将来拡張**: ルーティングがカバレッジ/コストを改善する場合、実際の独立dFBA軌跡で訓練を拡大。学習された完全フラックス/双対ウォームスタートは別の統合段階。

**既存のソースモデル/コンパイラフィンガープリントと数値ゲートが引き続き権威を持つ。生産CPU/GEMデフォルトは変更されない。ホストはLPをアセンブルしdFBA状態を統合する；これは完全なGPU常駐ではない。**

### 1.3 実装済みパイロット詳細

- **ネットワーク**: 小規模64隠れユニットtanhネットワークが開始基底を選択。推論はGPU行列演算で、オンラインPyTorch依存やCPU LP呼び出しなし。
- **検証**: 元の完全変数メカニズム再構築と数値的実行可能/双対/ギャップテストは必須。GPU修復は高価な網羅的銀行スキャンより先に試行され、拒否された行のみがスキャンにエスカレーション。
- **合成データ**: 既存のオフラインアンカーからLPパラメータを補間。完全な銀行によって独立に保証されたサンプルのみが分類ラベルを提供。
- **パイロット結果**: 段階あたり512例試行；210/130/177が保証。3モデルはそれぞれ4,484/5,324/4,868パラメータ。
- **訓練時間**: GPUの教示・訓練に47.59秒、新たなCPU LP求解はなし。アンカー銀行構築のCPUコストはプロvenanceの一部。
- **コンパイル問題**: 初回実行でCUB/ヘッダコンパイルエラー。再実行では`CUPY_ACCELERATORS=''`（標準CuPy GPUカーネル）を使用。パッケージ/CUDAヘッダの変更なし。ベンチマークは同じ設定を使用すべき。
- **コードテスト**: 11のターゲットテスト合格（意図的に間違ったニューラル提案、非有限入力、アーティファクト恒等性、GPU修復、正確な二次LP保証を含む）。

### 1.4 実際の軌跡訓練とアブレーション

- **合成ルーティングの移行失敗**: 8環境の1ステップ実行はエンドポイントゲートを通過したものの、4ワーカーCPUより遅かった。2ステップでは依然として第2段階の2つのLPが拒否された。**合成トップ1精度をロールアウト性能と解釈しないこと**。
- **32独立訓練軌跡収集**（シード20286701–20286732）、各2ステップ：192 CPU LP呼び出し、110.74秒（準備含む）。教示・訓練を加えて合計121.81秒。各段階に64実LP例。軌跡全体を訓練/検証グループに分割；ベンチマークシードは別途除外。
- 第2段階ルーティング検証トップ1は**57.1%**。完全LP保証は依然として必要。
- **共有エンジニアリング修正**:
  - 修復キャッシュを4から8エントリに拡張
  - GPUピボット内の冗長な双対求解と転置積を削除
  - 28のターゲットテスト合格

- **ニューラルルーティング**：控えめに高速だが統計的に確立された優位ではない。集計段階ピボット数は55（定数基底）から15（学習基底）に減少（同一8環境合計）。準備段階時間は0.4176秒から0.1990秒に短縮。これはこれらの入力での初期化改善の証拠であり、全媒体または長期間軌跡への一般化を主張するものではない。

- **2ステップテスト**（`pf_amn_actual8_step2_20260904.json`）：第2集計LPで停止、8行中2行が未保証。全環境が1ステップのみ完了。GPU失敗時間9.241秒は、完全CPU 2ステップ時間7.028秒との比較にはならない（成功した高速化として）。

- **最終回帰テスト**: 29合格（`pf_amn_final_tests_20260904.log`）。

## 2. 状態遷移カバレッジとGPU修復計画

（出典: `AMN_TRANSITION_SCALING_20260904.md`, 2026-09-04）

### 2.1 問題と診断

- 以前のルーターは段階あたり64 LP例のみ（32軌跡 x 2ステップ）。PPOタイムステップ増加はこの初期基底ネットワークを訓練しない。
- 失敗した第2ステップ集計行：原始残差は約1e-12だが、双対違反0.374/1.449、64ピボット後も大きなKKTギャップ。これは未解決の最適化問題であり、生物学的制約が実行不可能である証拠ではない。

### 2.2 作業順序

1. **訓練拡大**: 64軌跡 x 8ステップ = 段階あたり512 LP、1,536オフラインCPU LP求解（前回の8倍）。
2. **特徴選択修正**: 訓練軌跡からの可変入力を選択（小規模アンカー銀行のみでなく）、ホールドアウト軌跡は除外。
3. **短期代替基底GPU修復追加**：長期予算を不良な開始点に費やす前に実行。元の制約/保証を保持し、失敗時は閉じる。
4. **比較**: 2ステップおよびより長い完全ロールアウトを4ワーカーCPUと比較。コールドセットアップ/オフライン訓練と準備済み実行を分離。
5. **記録**: 改善と共に失敗とコストも記録。完全環境パスが資格を得るまでは、PPO実行や完全デバイス常駐dFBAの主張なし。
6. **8ステップは中間デバッグ間隔**であり最終ホライゾンではない。完全120ステップオフライン軌跡を収集して後期枯渇・蓄積をカバー。最終精度/速度検証には、分離された完全120ステップ軌跡を使用しなければならない。

### 2.3 中間実験

- **64 x 8訓練完了**: 1,536 CPU LP呼び出し；692.11秒（他の診断プロセスも同時実行）。集計銀行は直接512入力中12のみ保証。分類器例だけでは不足する基底を追加できない。
- **短期代替基底ポートフォリオ**：最終2行を解決できず；オプトイン診断として保持、デフォルトでは有効化しない。
- **失敗LP解析**: 163ピボット（Dantzig価格設定）で収束した失敗クエリもあり、Devex近似加重ルールでは71ピボットで収束。これは生物学的非実行可能性ではなく、サイクリングや一般的な高速化の証明でもない。
- **注意**: 価格設定変更は原始/双対/ギャップゲートを変更しない。近似実装はHiGHSの正確な急峻端エッジやDevex参照リセット機構の完全再現ではない。
- **キャプチャ/リプレイテスト**: 新しいエッジ重みにおけるインプレース状態更新問題を発見・修正。eager/リプレイされた重み/ピボットはテストで一致。
- **8環境128ピボット診断**: 集計拒否が2行から1行に減少。既存の12基底すべては、別の網羅的プローブで128ピボット以内に残りのホールドアウトLPを解けなかった。訓練と診断が重複：これらの実行時間はクリーンなハードウェア速度比較ではない。
- **独立予備辞書**: 8個の新しいシード x 4ステップ、32集計アンカー。未解決の集計行のみがこの広範な辞書を参照。
- **全ホライゾンオフラインデータ**: 4個の新しいシード x 120ステップ（1,440 CPU LP呼び出し）、正規化入力を将来の再ラベルリング用にキャッシュ。これは初期の後期状態カバレッジであり、統計的に十分な検証ではない。

### 2.4 メモリとデータセット統合

- 4つのオフラインCPU軌跡すべてが120ステップ完了。64 x 8データセットと4 x 120データセットはシードが互いに素。ジョイントトレーナーは各データセットの軌跡ホールドアウト分割を保存し、記録された特徴IDの共通部分を使用；欠損特徴は作成しない。
- 結合提案訓練セット：段階あたり992 LP例（分割前）。
- **32アンカー予備ベンチマーク**：約7.9 GB VRAMに達し、大きな実行速度低下。明示的に終了・中断としてマーク；速度比較ではない。物理VRAMほぼ満杯；特定の転送/ページング機構はプロファイリングされていない。
- 保持されたオフライン辞書は変更なし。時間階層化ロード（ステップ2アンカーのみ、再実行前に宣言された8候補）がデバイスストレージを制限。これは明示的な設定ロードであり、自動GPU常駐ページングではない。
- **回帰テスト**: 36合格、3予想警告（ジョイントモデルベンチマーク前）。特徴アライメント、軌跡分割保存、予備/ポートフォリオ保証、非実行可能拒否、eager/リプレイエッジ重み一致をカバー。
- **残存集計LP**: 新しい予備基底から82ピボットで収束。最初の予備実装は部分的な32ピボット進行を破棄；選択的ウォーム継続がそれを保持するよう修正。
- **ジョイント早期/長期ルーター**: 段階あたり992例で訓練、ホールドアウトトップ1精度0.960/0.746/0.906（ルーティングラベル指標、フラックスや軌跡精度ではない）。
- **8予備/8修復キャッシュ実行**: 7.95 GBに近づき、GPUタイミングを返す前に終了。グラフキャッシュ解放をソルバー退避時に追加して、ソルバー/グラフ/ウォームオーナー参照サイクルを切断。参照されたウォーム状態配列は有効。有界3ソルバー修復キャッシュを次にテスト；キャッシュ容量は許容誤差変更ではない。

### 2.6 更新された次の優先事項

1. 交換最小化LPに長ホライゾンカバレッジ/初期化と保証継続を適用；その銀行は依然として4基底のみ。追加された絶対交換変数/制約をまたいで、前段階の実行可能状態を転送する可能性を調査（実行可能性から遠く離れて再起動するのではなく）。**客観的一致と交換精度を同一視しないこと**。
2. 辞書とグラフメモリを独立に制限。完全精度の元の制約チェックを保持；使用量を示すためだけにVRAMを満たさない。
3. 完全2/8ステップロールアウト、次に完全120ステップ開発ロールアウト、その後新鮮な独立120ステップ精度・スループット実行を再テスト。
4. 修復率学習曲線が不十分な後期状態カバレッジを示す場合、4長軌跡を超えて拡大。4軌跡は後期例を提供するが、120ステップカバレッジが統計的に十分であるという証拠ではない。

## 3. 食い違いに関する注記

本統合文書内で認識されている食い違いはありません。各ドキュメントは連続したイテレーションを表し、後続のドキュメント（`AMN_TRANSITION_SCALING_20260904.md`）は先行ドキュメント（`AMN_GUIDED_ACCELERATION_PLAN_20260904.md`）で報告された問題に取り組み、以下の進展を報告しています：
- 第2段階集計LP失敗（以前は2行未解決）→ 特定の構成で解決
- 訓練データ規模（段階あたり64例 → 992例）
- 最終テスト数（29 → 39）

いずれの場合も、後続の結果が先行の結果を置き換えるのではなく、状況を更新しています。項目1.5（計画の測定結果）で報告された数値は、状態遷移計画（2.5節）で報告された数値とは異なる前提・データセットに基づいており、直接比較できません。
