# 検証付きGPU基底辞書とCPU再最適化による反復dFBAの高速化

更新日: 2026-09-04（固定条件の独立seed検証完了を反映）。対象: OR16、NS21、P. freudenreichii のcommunity dFBA。本文は実装、開発用測定、および限定条件の検証記録であり、学習済み制御器の性能または実培養での妥当性を示すものではない。

後続の2026-09-05の実装・測定・計画改訂は [改善計画 Revision 1–5](GPU_HYBRID_ACCELERATION_20260905.md) に分離して記録した。hostの同値改善、全辞書診断、限定GPU補正の結果を含む。本稿の固定検証のsource・数値は後続実装へ置き換えない。

## 1. 結論と対象範囲

現方式は、事前計算したLP基底からGPU上で候補解を復元し、元LPの制約・最適性を数値検証して採用する。未合格の問題だけを、計算予算を限定したGPU補正またはCPU HiGHSへ送る。CPUへ送る場合もGPUが選んだ基底を初期値として利用できる。したがって「全LPをGPUで解く方式」ではなく、正しさを検証するGPU優先ハイブリッド方式である。

実装は `src/gpu_hybrid_lp.py` の再利用可能なバックエンドとして追加し、`scripts/benchmark_compact_gpu.py` で実際のcommunity dFBAへ接続して検証した。学習エントリポイントの既定経路をこの方式へ切り替えたわけではなく、今回の速度値は強化学習全体の実行時間ではない。

32環境×2時間ステップの開発用比較では、同じ辞書で初期化するpersistent CPU基準との時間比（CPU/ハイブリッド）が1.031、1.118となった。その後、設定を固定した非重複seed群の5組のgraph再利用条件で、時間比の幾何平均1.0632、対応対数比のt法95%信頼区間1.0182–1.1102を得た。オンライン平均時間はCPU 13.932秒からハイブリッド13.098秒となり、総時間は5.99%短縮した。

これは短時間遷移・32並列という限定条件の結果である。n=5のt区間は対数比の独立性・概ね正規的な分布を仮定し、補助的な両側符号検定はp=0.0625であった。一般的な速度優越性や120ステップでの持続性は未確認である。採用した開発用・独立検証条件はいずれもGPU補正ラウンド0で、独立warm検証のLPの61.875%はCPUへ戻っている。この結果を「分散に応じたGPU補正の有効性」や「完全GPU化」と解釈してはならない。

後続の大辞書・環境別4候補バッチによる32環境×8ステップ比較は、CPU/ハイブリッド比1.0527と0.9809で、精度は両組合格したが速度は正負に分かれた。8ステップでの一貫した優越性は未達である。最新結果と残る律速は第8節に示す。

## 2. 計算対象と時間依存性

各環境では、培地・菌体量等からLPを構築し、maxmin、aggregate、exchangeの元の3段階目的を順番に解き、得られた交換・増殖フラックスで状態を更新する。1ステップは0.2時間、今回の2ステップは各環境の培養0.4時間に相当する。時間方向には前後の状態依存があり、独立して並列化する単位は環境群である。

FBAでは同じ最適目的値を与える内部フラックスが複数存在する。交換フラックスまで非一意なら次時刻の状態が変わるため、CPU/GPUの比較では目的の優先順位と許容差をそろえる。3段階目的だけで全交換フラックスの数学的一意性が保証されるとは主張せず、培養軌跡と終点を追加検証する。[DFBAlab](https://pmc.ncbi.nlm.nih.gov/articles/PMC4279678/)

## 3. 実装アーキテクチャ

| 処理 | 現在の役割 | 正確性・性能上の注意 |
|---|---|---|
| オフライン基底辞書 | 学習用LPの基底・写像・入力特徴を保存する。モデルfingerprintと入力族を管理する | ニューラルネットのオンライン学習ではない。評価中のCPU解は辞書へ追加しない |
| 候補の選択と復元 | 現在のLP入力に対し近傍候補等を並べ、compact写像で候補解をGPU上に復元する | 候補の近さは正しさの証明ではない。基底が許す範囲を外れた候補を採用しない |
| cohort一括検証 | 共通候補集合を環境群に適用し、候補復元・証明・選択・分散集計を単一CUDA graphとして再実行する | 候補別host dispatchを減らす。行列演算量そのものが消えるわけではない |
| 元LPの証明 | 主実行可能性、双対実行可能性、相補性に基づく相対KKT gapを検査する | 圧縮空間だけでなく元の全LPを検査。浮動小数点許容差内の証明であり厳密有理数証明ではない |
| 限定GPU補正 | 未合格で低分散の候補について探索方向を制限し、予算内で補正する任意機能 | 補正後も同じ元LP基準を要求。今回の採用開発条件・固定独立検証では無効 |
| CPU fallback | 高分散・分散不明、またはGPU補正予算終了後の未合格問題をpersistent HiGHSで再最適化する | GPU候補基底は初期値にすぎず、HiGHSの最適終了と元LP証明の両方を要求する |
| 状態更新 | 合格したフラックスを用いてhost側dFBAを進める | LP入力組立、経路振り分け、CPU補正、状態更新はGPU内完結ではない |

GPU/CPUで共通の採用基準は、元座標の主残差最大値 ≤ `1e-5`、双対違反 ≤ `1e-7`、相対KKT gap ≤ `1e-7`。目的値だけの一致では採用しない。有限値、入力族、モデルの対応も確認する。

CUDA graphの再利用は、短いkernel群を1回のlaunchにまとめ、CPU起動費用を反復間で償却する既存技術に基づく。固定shape・参照バッファの寿命を守り、入力値だけを更新する。初回capture/instantiate費用と再実行時間は分けて記録する。[NVIDIA CUDA Graphs](https://developer.nvidia.com/blog/cuda-graphs/)、[固定アドレス・形状等の制約](https://docs.nvidia.com/dl-cuda-graph/cuda-graph-basics/constraints.html)

主な実装: `src/gpu_compact_basis.py`、`src/gpu_hybrid_lp.py`、`src/gpu_restricted_basis.py`、`src/cpu_repeated_lp.py`、`src/cpu_dictionary_lp.py`。比較実行は `scripts/benchmark_compact_gpu.py` を使用する。

## 4. 分散による振り分けと限界

観測射影は、種別増殖速度、種別交換フラックス、PHA/PHB/PHV関連反応速度で構成し、内部循環フラックスと絶対値用補助変数を除く。候補間の各成分の標本標準偏差を明示的な尺度で割り、最大成分を分散指標とする。現実装の尺度は各成分1であり、実験データから校正した誤差確率や物理的不確実性ではない。異なる単位の成分をまとめるため、閾値の校正が今後必要である。

振り分けは次の順序とする。

1. 元LP証明に合格した候補を優先して採用する。高分散でも合格をCPUへ戻さない。
2. 未合格で、候補数不足または分散非有限なら「分散不明」としてCPUへ送る。
3. 未合格で分散が閾値を超える場合はCPUへ送る。低分散なら任意の短いGPU補正を試す。
4. GPU予算後も未合格なら、低分散でもCPUへ送る。

分散が大きくても複数候補が同じ最適面の正しい解である場合があり、逆に候補が一致していても全候補が誤る場合がある。このため分散は補正の難しさを調べる特徴であり、採用ゲートではない。最適解の非一意性と基底の非一意性も区別する。[DFBAlab](https://pmc.ncbi.nlm.nih.gov/articles/PMC4279678/)、[SurfinFBA](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1007786)

現在の閾値は実験的ルールであり、残差減少率・候補数・転送費用を含むGPU/CPU所要時間予測器は未学習である。「分散が大きい場合だけCPUへ戻すと最速になる」という保証はない。

## 7. 多GPU化の設計案と未達事項

第一候補は環境群・seed・agentをGPUごとに分ける独立shard方式である。各GPUに辞書と担当環境のバッファを持たせ、環境の時系列は同じshard内で進める。CPU fallbackは共通の上限付きworker poolで管理し、CPU競合・転送・負荷偏りを測定する。VRAMが自動的に共有される方式ではなく、3基で3倍になる保証もない。

1個の巨大LPを複数GPUへ分割するPDLP研究は、行列分割と反復ごとの通信を必要とする。小規模LPでは通信費用により遅くなる結果も報告されており、本系ではまず独立環境shardが適切と考える。これは文献からの設計上の推論で、多GPU実測は未実施である。[Li et al., Beyond Single-GPU, 2026](https://arxiv.org/abs/2601.07628)

達成範囲と残る未達・未検証事項を次のように区別する。

- 完全GPU内完結: host状態更新とCPU fallbackが残る。
