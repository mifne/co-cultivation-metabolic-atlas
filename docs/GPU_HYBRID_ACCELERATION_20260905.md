# 2026-09-05 改善計画: 後半LPの採用率とhost律速の切り分け

## Revision 1 — 計測前に固定する方針

前日の固定32環境×2ステップでは約6%短縮したが、最新32×8ではCPU/ハイブリッド比1.0527と0.9809で、持続的な優越性は未達。約53秒のうち、その他host dFBA処理は約21秒、CPU fallbackを含むその他LP処理は約27秒。後半のaggregate/exchange辞書採用率がほぼ0%である。

目的は同じ元3段階LP・同じ状態更新・同じ精度ゲートのまま、8ステップ以降の総時間を減らすこと。GPU占有率そのもの、近似解の無条件採用、比較CPUの不当な弱体化を目標にしない。過去の固定検証は変更しない。

1. host側の関数別profileを採取する。LPサービス呼出し中は主スレッドprofileを停止し、待ち時間をhost関数の費用と誤認しない。profile有効時の秒数は通常の速度比較に用いない。
2. 保存済み候補診断から、K候補選択、入力族、主残差、双対違反、相補性gapを切り分ける。証拠がない項目は未判定とする。
3. 支配的なhost処理を厳密同値な変更で最適化し、変更前後の入力・状態・解の比較と回帰テストを行う。共通改善はCPU側にも適用する。
4. GPU側は低採用率の原因に応じて、候補選択・必要時のみ追加候補・補正処理のうち最小の介入を選ぶ。辞書の一律拡大を先に決めない。
5. 開発用の新seed群で32×8をCPU/GPU交互順に比較し、すべての成功・失敗・遅延を残す。設定変更ごとにsource snapshotを保存する。結果を見てRevision 2以降へ計画を更新する。

確認基準は元LPの主残差≤1e-5、双対違反≤1e-7、相対KKT gap≤1e-7。終点PHA相対差≤1%、菌体量最大絶対差≤0.01 g/L、PHV比率絶対差≤0.01。入力・モデルfingerprintおよび学習/評価seed分離を維持する。

120ステップ・実RL・多GPUへの外挿は、8ステップで一貫した改善の確認後に別々に検証する。

### 次に取り組む順序と計画の更新条件

1. **主対象をaggregate/exchangeの基底被覆不足に置く。** 32×8の最後の組のLPサービス時間はmaxmin4.649秒、aggregate10.665秒、exchange13.065秒である。maxminは総時間の約11.4%に過ぎず、その高速化だけに追加開発を集中させない。全辞書診断でもaggregate1/32、exchange0/32だった。前時刻の合格基底の再利用、目的段階ごとの学習用active-set被覆、全空間へのGPU修復を比較する。元の階層目的・培地更新は変えず、評価中のCPU解をオフライン辞書へ混入させない。一律の辞書拡大より先に、何件を救済できるかと1件当たり費用を測る。採用率が低い段階の直接CPU経路も対照に加え、無効なGPU探索の費用を分離する。
2. **GPU補正の準備費用を償却できるかを限定実験で判定する。** operatorおよび基底・batch形状別graphのcache hit/miss/eviction、初回・再利用時間、保持VRAMを明示する。学習用データから決めた常駐集合とメモリ上限で比較し、評価LPから都合のよい集合を選ばない。prewarmする場合は起動費用を別記し、起動込み総時間と継続実行の両方を報告する。初回費用が残るため、cache増量だけを解決策とはしない。
3. **異なる候補基底を含む補正をまとめる。** 現在は基底ごとの逐次group処理で平均1.29件となる。異種基底バッチ、または正確性を保つ固定shape bucketを小さく実装し、padding行が採否や状態更新に混入しないテストを先に行う。個別LPを解く費用より、起動・準備・同期が支配するかを再計測する。maxminで費用を切り分けた後、主対象のaggregate/exchangeへ適用できる構造にする。
4. **hostの残存費用も並行して追う。** 通常32×8の最後の組は40.766秒のうち、LP準備1.534、候補検査2.896、その他LP処理23.949、host dFBA12.387秒。その他LP処理はCPU fallback・待機・転送等の合計で、すべてCPU計算と断定しない。hostも約30%残るため、GPU演算だけの高速化では全体は比例して速くならない。境界判定の動的整合性を守りつつ、共有静的情報と配列化を次のprofileで再選別する。
5. **次の測定ごとに採用・棄却を明記する。** 小規模の同値・実行確認 → 新規seedの32×8交互順比較 → 構成を固定した独立反復 → 120ステップ → 実RL、の順とする。性能測定と精度確認は小規模から同時に行い、長時間の最終精度検証だけを先行させない。小規模で遅い方式でも大バッチで償却の根拠がある場合のみ次段階へ進める。

## Revision 6 — 基底の時間変化と問題表現を見直す

ユーザーの根本的な修正を含む依頼を受け、次の実装前に時系列の基底再利用とLP表現を監査する。32×8の最後の組ではaggregate244件中212件、exchange246件中191件がCPUの前回基底を再利用しており、それでもCPU反復数は46,902 / 22,790である。単に「CPU側が毎回cold startだから遅い」とは説明できない。exchangeは疎構造変化による追加rebuildも23件ある。

優先する調査は、(1)前時刻基底のGPU再構成が何件通るか、(2)exchange補助変数や固定変数を元LPの最適性証明を維持して縮約できるか、(3)不採用が多い段階の探索費用を削減できるか。少数環境で元LP・終点精度と準備込み費用を確認し、有望な方式を新規seed・32環境へ進める。処理の省略や変数消去が目的の順序・交換フラックスを変える場合は、単なる同値最適化とは扱わず別案とする。

## Revision 7 — 計算を重ねるスケジューリングへ拡張

構造監査ではexchangeの639補助変数中633本が双方向で、符号確定だけによる削減は小さい。時間基底の有効率は別probeで測る。一方、現行schedulerは全環境の各LP段階をbarrierとして待ち、LPサービス外のhost状態更新約12秒とCPU LP処理が直列になる。

maxminをGPU全環境バッチ、aggregate/exchangeをexact CPUへ送る段階別経路を追加し、4×8の新規2組で精度合格を確認した。CPU/hybridは5.671/6.177秒、6.014/6.084秒で小規模では高速化未達。この経路を土台に、CPUのaggregate/exchangeを環境ごとに非同期実行し、完了した環境のhost状態更新を主スレッドで進める。次時刻のmaxminまでに同じ全環境を揃えるためGPUバッチは維持する。

CPU比較にも同じscheduler、同じworker数、同じoffline初期基底、同じ状態更新を適用する。COBRA/greenletは主スレッド、workerはLP配列のみとする。非同期の段階別経過時間は重なるため合算せず、待機・主スレッド処理等の非重複wall区間を別記する。小規模で順序・例外時join・元LP証明・終点一致を確認後、32環境で効果を測る。

### 時系列・構造診断の結果

`results/pf_temporal_basis_validity_4x8_20260905.json` はseed20292001–04、0.2時間刻み、各環境8ステップを完了した。各環境のstep2–8で直前の合格HiGHS基底を現在のLP行列で再構成すると、aggregate0/28、exchange0/28だった。両段階で27/28件が主実行可能性基準を超え、双対またはgap超過も重複して生じた。現在基底を疎LUで毎回再構成した診断であり、GPUの速度測定ではない。

後続のCPU最適化で変化した列status数の中央値はaggregate47、exchange66.5、CPU pivot中央値37.5 / 94だった。これらは最小必要pivot数ではない。今回の状態・基底選択では無補正の前基底写像だけでCPU呼出しを省く根拠が得られなかったため、無条件の動的辞書追加は進めない。

[SurfinFBA](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1007786) は基底が有効な区間の再利用を示すが、将来方向に適した退化基底の選択も必要とする。今回の0件は同手法一般の否定ではない。[mpFBAの研究](https://arxiv.org/abs/1802.02567)も、代謝モデルの縮退・多重最適性を扱う必要を示す。将来の動的写像生成には[HiGHSのbasis solve API](https://ergo-code.github.io/HiGHS/stable/guide/advanced/)を使い、全逆行列でなく実変動方向の写像を取得する余地がある。ただし写像生成費が再利用による節約を下回ることを先に確認する。

静的LPテンプレートを追加した後の`results/host_profile_4x8_static_templates_20260905.json`は、変更前の`host_profile_4x8_optimized_bounds_20260905.json`に対して全96 LP入力hashと全終点が完全一致した。固定の等式構造・目的配列・exchange列配置を共有し、状態依存の係数・RHS・上下限は毎回更新する。profile上のassembly費用は元々小さく、これ単独で大幅な速度改善とは主張しない。
