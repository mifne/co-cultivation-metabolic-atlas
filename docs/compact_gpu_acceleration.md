# GPU加速dFBA/LPソルバー開発統合ドキュメント（2026-09-04）

**要約**：本ドキュメントは、GPUを活用した微生物代謝モデル（GEM）の動的フラックスバランス解析（dFBA）の高速化に関する計画、実装、評価結果を統合したものです。CPU基準（HiGHS 3段階、4並列ワーカー）に対する高速化は未達ですが、低次元縮約＋継続的列生成によるGPU専用解法の開発が進み、8環境×2ステップの短軌道でCPUの0.449～0.859倍の性能（GPUが低速）まで改善しています。全変数GPU補正やオンラインCPU LPへのフォールバックなしで全LPを解けたことが確認されましたが、CPU超えには至っていません。ホスト側の状態更新・LP組立は残っており、完全なGPU resident dFBAではありません。

---

## 1. 背景と受け入れ基準

**出典**：`docs/COMPACT_GPU_ACCELERATION_20260904.md`（2026-09-04）

- **比較条件**：同一のGEM、初期状態、操作系列、環境数、完了ステップ数。CPU基準は変更なしの3段階HiGHS、4並列LPワーカー、1LPあたり1スレッド。
- **オンラインGPUパス**：CPU最適化を呼び出してはならない。ホスト側の環境組立は計測対象に含める（完全なデバイス resident ではない）。
- **精度基準**：
  - 元LP：primal feasibility ≤ 1e-5、dual violation ≤ 1e-7、relative KKT gap ≤ 1e-7
  - 軌道終点：PHA相対誤差 ≤ 1%、biomass絶対誤差 ≤ 0.01 g/L、PHV分率絶対誤差 ≤ 0.01
  - 高速化のために基準を緩めない。
- **速度報告**：すべてのゲートを通過した完了一致作業のみ。コールドセットアップ、オフライン準備、反復実行は分離。短い結果は120ステップの結果としない。

## 2. 初期の計画と試行（Revision 1～13）

**出典**：`docs/COMPACT_GPU_ACCELERATION_20260904.md`

### Revision 1：コンパクト基底マップ

- 以前の8環境試行は2ステップ中1ステップしか完了せず、交換最適化で7/8環境が拒否された。CPU 7.206秒(2ステップ)に対しGPU 17.689秒(不完全)。比較不能。
- コンパクトアーティファクトの作成と検証、トレーニング軌道からのコンパクトバンク構築、一致2ステップ計測を計画。現状：実験的コードは存在するが、速度向上は未確立。

### Revision 2：コンパクトスクリーニング＋小規模GPU修復

- 構築済みバンク（44 maxmin, 52 aggregate, 44 exchange、約327.7 MB、110.69秒）は4つの試験に合格。しかし8×2テストで6/8行が拒否。拒否行の残差は1.9e-5～0.94。基底の拡大だけでは訓練サンプル間の実行可能性を保証できない。
- コンパクトスクリーニングを維持し、ミス発生時は既存の全変数GPU補正を復元する方式を採用。

### Revision 3：違反制約数によるランク付け、候補評価の再利用

- オフライン修復演算子構築は265.66秒で完了（CPU LP解決ゼロ）。48ピボットで8×2テストのステップ1は終了するが、ステップ2 aggregateで4/8拒否。128ピボットでも1行拒否。速度向上なし（CPU約7.1～7.4秒、GPU約16.3秒、不完全）。
- 双対実行可能性優先、違反数・L1ノルムによるランク付けを追加。候補評価の再利用、CUDAグラフ再生を導入。

### Revision 4：GPU生成訓練プレフィックスの収集

- 新しい4プレフィックス軌道（26.63秒）で再構築したバンクはステップ2 aggregateを約2.70秒に改善するが、交換段階で128ピボットでも4行拒否。プレフィックスカバレッジだけでは不十分。
- 反復改良の追加（終了時だけでなく各反復で）を計画。

### Revision 5：GPUピボット更新の安定化と圧縮

- 384ピボット＋反復改良で記録的な困難ケースが156ピボット/123更新位置で元LP証明書を通過（約6.39秒）。ただしこれはエンドツーエンドの速度向上ではない。

### Revision 6：合体小規模求解、短ポートフォリオ、メモリ制約付き継続

- 384ピボット完全軌道試行で1行拒否。別の基底では39ピボット（約0.38秒）。密度求解カーネルを共有メモリ最適化し、同156ピボットを2.40秒に短縮。ポートフォリオ試行はメモリ不足で終了（7949 MiB）。

### Revision 7：ルーティング修正と元の3段階問題への一致

- ルーティングバグ（1e20加算によるスコア消失）を修正。32ピボット探索を64ピボットに変更。全8環境がステップ2まで通過。しかし第4のタイブレークで6行拒否（相補性ギャップ1.2e-7～3.8e-7）。
- `original3`比較モード：CPU参照と同一の3目的関数を使用。8×2 original3比較：CPU 7.093 / 7.233秒、GPU 31.604 / 23.128秒（比率0.224 / 0.313）。有効比較だがGPU低速。

### Revision 8：環境数増加前のメモリ制限

- 64×2試行：CPU 55.418秒、GPUは10分超で7939 MiB使用、メモリ圧力により終了。ウォーム状態が大規模GPUソルバーを保持していた問題を修正。修復グループを環境数とは独立に制限。

### Revision 9：小規模システム因数分解の再利用

- メモリ制限16×2：CPU 14.271秒、GPU 54.605秒（比率0.261）。交換修復だけで31.068秒。各基底更新後にLU因数分解を一度計算し、複数の右辺に再利用。同じ困難ケースが153ピボット→1.581秒に改善。次の16×2：CPU 14.642秒、GPU 50.246秒。まだCPU超えず。

### Revision 10：修復コストルーティングの評価

- 双対実行可能性優先では違反制約数326の候補を選ぶが、別候補は約6。低違反候補から52ピボット/0.599秒で成功（vs 153/1.581）。このルーティング変更は8×2の独立比較で3行不合格。不採用。

### Revision 11：デバイス上の不要な双対作業のスキップ

- 条件付きノードで、双対シンプレックス不要な環境の双対計算をスキップ。同じ52ピボットを0.438秒に短縮。`count_only`ルーティングは不合格。次の64×2は修復グループ4、キャッシュ2で試行。

### Revision 12：構造的縮小の監査、反復改良の条件化

- 全訓練入力480件の監査：固定変数は11、等号制約でさらに429変数がゼロ。縮小可能なのは約6%。GPU専用の反復改良トリガーを追加。16×2のベスト：CPU 14.588秒、GPU 39.464秒（比率0.370、2.71倍遅い）。

### Revision 13：プライベートグラフプールの制限と認定GPU基底の再利用

- 2つ目の64×2試行もメモリ不足で終了（7947 MiB）。グラフキャッシュサイズを明示的に制限。時間的基底更新（Woodbury）を実装。8×2時間比較：CPU 7.198 / 7.276秒、GPU 27.878 / 20.470秒（比率0.258 / 0.355）。まだCPU超えず。これが低次元アプローチ前のベスト構成。

## 3. 低次元アプローチの設計と実装（Revision 14～19）

**出典**：主に`docs/COMPACT_GPU_ACCELERATION_20260904.md`（Revision 14～19）、`docs/REDUCED_GPU_IMPLEMENTATION_REPORT_20260904.md`（実装詳細）

### 3.1 適応的縮小空間最適化の設計（Revision 14：設計案、未実装）

- フラックスを v = v_ref + D z と表現し、小さな方向集合を適応的に拡大する方式。構造的化学量論的等式制約を保持する。
- 元LPの残差と双対最適性チェックで受入判定。PCAの説明分散率では代謝・軌道ゲートを代替できない。
- 初期次元候補：32/64/128（実験的スイープ値）。外分泌交換、biomass、PHA感受性方向を含める。既存の全変数GPUソルバーを最終安全層として保持しながら開発。

### 3.2 制限列表実装と初期テスト（Revision 15～16）

**Revision 15**：
- M×K縮約表：非基底方向K本を選び、基底変数を消去。縮約表のみGPUでピボット。最終基底の正準化には最大K回の置換。元LP証明書は変更なし。
- 最初の困難ケース（candidate 2）はK=16/32/64/128で不合格（2/4/7/53縮約ピボット、0.11～0.28秒）。無効な部分解。方向選択と数値安定性を調査。

**Revision 16**：
- 低違反候補はK=32でprimal feasibleになるが、全空間双対最適性は未達。除外方向を価格付け（primal feasible時は原目的、非 feasible時はPhase I）。適応的価格付けによりcandidate 13はK=256で全LP通過（41縮約ピボット、約0.437秒）。candidate 2は依然として不合格。
- 縮約試行を全変数修復の前に配置。短いGPU polishを縮約成功後にのみ試行。47回帰テスト合格。

### 3.3 継続的列生成とメモリ最適化（Revision 17～19）

**Revision 17**：
- 最初の統合8×2：CPU 7.198 / 7.105秒、GPU 33.784 / 101.519秒。繰り返し実行で深刻な低下。cuBLASハンドルのリークを修正。全空間双対違反が大きいのは方向不足が原因であることを確認。
- 継続的列生成を実装：直前のGPU基底を保持、小さな非基底プールを再価格付け、M×K表を再構築。表の幅Kと基底差分ランクは別。記録的な困難ケース（row 2/candidate 1）はK=64で12ラウンド、row 3/candidate 13は2ラウンド（約0.272秒）。診断的な観測値。

**Revision 18**：
- 継続的列生成8×2：精度通過、オンラインCPU LPゼロ、全変数補正呼び出しなし。しかしGPU 35.649 / 73.721秒でCPU超えず。メモリ約8 GB。
- グラフ終了時にプライベートプールの未使用ブロックを明示的に解放する修正。単一LP診断でデバイス使用量が2.699 GB→1.719 GBに減少。メモリ修正後8×2：CPU 6.993 / 8.781秒、GPU 21.685 / 17.168秒。繰り返し実行の低下は除去されたが、GPUは依然として低速。53回帰テスト合格。

**Revision 19**：
- 任意の早期ウォームスタートパス（ステージ1→aggregate）は8×2で遅くなる（GPU 48.706秒）。不採用。
- ランクバケット（容量を2のべき乗に揃えてグラフ再利用）を実装。記録的な困難ケースでは約0.74秒で全ラウンド完了。バケット化8×2：CPU 7.064 / 9.333秒、GPU 15.735 / 10.862秒（比率0.449 / 0.859）。繰り返し実行もCPUより低速。
- 既存の大きい辞書（44/52/44）を組み合わせた16×2：CPU 14.672 / 15.129秒、GPU 55.742 / 41.770秒。辞書サイズ拡大は速度向上に直結しない。

**重要**：64環境×2ステップ（修復グループ4、キャッシュ2）の試行は、第2交換段階で約7900 MiBに達し終了。CPU 55.849秒だがGPUの完了時間・速度比は存在しない。全ての計測は終了しており、バックグラウンドのベンチマークは残っていない。

## 5. 考察と残る課題

**共通の限界**：
- いずれの構成でもCPU超えの高速化は達成していない。ベストでCPUの0.449倍（GPUが2.23倍遅い）。
- ホスト側のdFBA状態更新・LP組立は残っており、完全なGPU residentではない。
- 120ステップや強化学習全体での計測は行われていない。2ステップの短軌道のみ。

**低次元アプローチの律速**：
- 縮約空間内で最適でも、未選択方向に改善余地が残るため、複数回の列生成が必要。64方向の計算自体だけでなく、方向選定・元LP検証・基底復元・グラフ作成と小グループのホスト制御が積み重なる。
- グラフ終了後の出力配列保持によるメモリプール確保問題は修正済みだが、多数環境では依然としてメモリ圧力が発生（64環境で約7900 MiB）。

**今後の優先課題**：
1. どの初期基底・方向選択が高コストな第2交換段階修復を引き起こすかを特定する。
2. 修復ワーキングセットをメモリ制約下に保つ。
3. 時間的基底再利用（同一LPの列生成継続とは別）を測定する。
4. 環境数を増やした場合の並列効率を、まず16環境で確認し、その後64環境、120ステップへ進める。高速化が確認されてから新しい独立シードで検証する。
5. ホスト側dFBA状態更新のGPU resident化は今後の課題。

**食い違いに関する注記**：
- 2つの元ドキュメント間で数値や結論に矛盾はありません。表の数値は完全に一致しています。
- `docs/COMPACT_GPU_ACCELERATION_20260904.md` のRevision 13で報告されたtemporal 8×2（CPU 7.198/7.276秒、GPU 27.878/20.470秒）は、低次元アプローチ以前の結果であり、上表には含まれていません。これは低次元アプローチの比較対象として参照できます。
