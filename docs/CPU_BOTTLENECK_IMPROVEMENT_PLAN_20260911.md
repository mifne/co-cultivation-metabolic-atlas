# 後段CPU完了待ち改善方針

根本原因診断([docs/MASTER_INDEX.md](MASTER_INDEX.md)の「GPU高速化関連ドキュメント」参照)で、
GPU高速化が進まない最大の要因は「後段CPU完了待ち」(GPUでLPを解いた後、ホスト側=CPUで行う
dFBA状態更新・次LP組立・認証等)が全体時間の過半を占めることだと判明した
(データフロー解析では54.3%、120step検証では合計898.378秒中約760秒(84.6%)が
後段CPU関連)。本書はこれを改善するための方針を、既存の試行錯誤とコード構造の
両方を踏まえてまとめる。

DeepSeek V4 Flashに、関連ドキュメント4件とソースコード8件(計約27万字)を読ませて
作成した([scripts/analysis/deepseek_delegate.py](../scripts/analysis/deepseek_delegate.py)、
コスト$0.016、Claude Sonnet 5換算$0.27の16.9倍安価)。コード中の関数名・処理内容は
実ファイルと照合して確認済み。ただし行番号は実際とズレがあったため本書には記載しない
(関数名で参照すること)。

## 1. 既に試された対策(繰り返さないために)

| 対策 | 結果 | 出典 |
|---|---|---|
| 非同期パイプライン(GPU計算中に他環境の状態更新を進行) | 8stepで4.66%短縮も120stepでは6.25%悪化。一貫した優位なし | dataflow_acceleration.md 3.2節 |
| Basis Handoff(GPU認証基底をCPUへ引き継ぎ) | 反復は29%減るが総時間は短縮せず。既定off | dataflow_acceleration.md 3.3節 |
| 証明再利用(zero-face証明の再走査削減) | 初回準備59%短縮もhot時刻は無改善(むしろ1.7%増) | gpu_batch_speed_optimization.md |
| Device常駐数値更新 | 係数更新は0.05〜0.07秒に短縮も、lifecycle全体はCPU16並列に届かず | gpu_batch_speed_optimization.md |
| 限定GPU補正 | 準備時間が84.5〜92.2%を占め総時間は悪化 | gpu_hybrid_lp.md |
| stream分割 | 分割するほど悪化(1x32が最速) | gpu_batch_speed_optimization.md |

**共通点**: いずれも「GPU計算の高速化」または「GPU-CPU間の非同期化」に焦点を当てており、
**後段CPU処理そのものの計算量削減・並列化には踏み込んでいなかった**。今回の方針はここを狙う。

## 2. 「後段CPU完了待ち」の正体(コード上の実体)

`src/community_solver.py`の`CooperativeCommunityFbaSolver.solve`は、maxmin→aggregate→exchangeの
3段階LPを同期的に実行する(各段階は`_solve_linear_program`経由でGPU/CPUどちらのバックエンドでも
完了までブロックする)。

段階間・ステップ間で発生する主なCPU処理:

1. **状態更新** — `src/audited_dfba.py`の`_integrate`。32環境分のバイオマス更新・交換フラックス集計・
   共有培地の濃度更新・酸素収支・pH計算・PHA上限チェックをPythonの逐次ループで実行。
2. **酸素カップリングの非線形求解** — `_solve_oxygen_coupled`。`brentq`による非線形方程式求解のため
   `solve_fba`を1ステップあたり平均3〜5回追加で呼び出す。
3. **数値認証と再試行** — `_certified_linprog`。主残差≤1e-5・双対違反≤1e-7・相対KKTgap≤1e-7を検査し、
   不合格時は`highs-ds`→`highs-ipm`の順に再試行。
4. **GPU側フォールバック** — `src/gpu_batched_compiled_backend.py`の`BatchedCompiledBackend.solve_batch`で
   不合格候補をpivot予算を変えて再試行し、最終的にCPUへ差し戻す。

## 3. 改善方針(優先順位順)

### 優先度1: 後段CPU処理のマルチスレッド/プロセス並列化

各環境のLP構築・結果変換・状態更新の大部分(生長率・PHB/PHV蓄積等)は環境間で独立している。
`concurrent.futures`で並列化する。共有培地(`changes`辞書)への書き込みのみ排他制御が必要。
酸素カップリングは共有酸素プールを介するため逐次実行のまま残る。

- **期待効果**: 後段CPU時間のうち並列化可能な部分次第だが、4コア並列で該当部分を最大4倍に短縮できる可能性。
- **難易度**: 中。COBRApyオブジェクトのスレッド安全性、`multiprocessing`を使う場合はシリアライズコストに注意。
- **既存対策との違い**: 過去の対策はGPU-CPU間の非同期化のみで、CPU処理自体の並列化は未着手だった。

### 優先度2: ステップ間オーバーラップの本格実装

`scripts/pipelined_microbatch.py`の`drive_pipelined`は`ThreadPoolExecutor`ベースの
`pending`/`wait`機構を既に持っており(`workers`パラメータあり)、部分的な非同期化の土台がある。
現状は1ステップ内のオーバーラップに留まっているため、aggregate完了環境から順次次ステップの
maxmin GPU計算を投入できるよう拡張する。

- **期待効果**: GPU使用率(現状6.8%)の底上げ。理想的には各ステップのGPU待ち時間の多くを隠蔽できる。
- **難易度**: 高。酸素カップリングが全環境の結果を要求するため完全なアウトオブオーダー化は難しく、
  GPUバックエンドの状態管理(段階別キャッシュ等)も複雑化する。
- **既存対策との違い**: 既存の非同期パイプラインはステップ内のみ。ステップ間へ拡張するのが新規性。

### 優先度3: 数値認証の条件付きスキップ

GPU側が既に元LP基準(主残差≤1e-5等)を満たした解を返している場合、CPU側`_certified_linprog`での
再検査を条件付きでスキップするオプションを追加する。

- **期待効果**: 小〜中。認証・再試行のオーバーヘッド削減。
- **難易度**: 低〜中。まずは監視モードで導入し、GPU解とCPU解の数値差が終点精度基準に影響しないか
  段階的に確認する必要がある。

### 優先度4: 酸素カップリングの近似高速化

`audited_dfba.py`は`shared_endpoint_v3`(非線形方程式、`brentq`で複数回のLP試行)と
`quota_mean_v2`(比例配分ベースの解析解、追加LP試行なし)の2方式を**既に実装済み**。
デフォルトを`quota_mean_v2`に切り替える、または試すだけで効果を確認できる。

- **期待効果**: 中。1stepあたり3〜5回の追加LP求解を1回程度に削減できる可能性。
- **難易度**: 低(既存オプションの切替)〜中(精度への影響検証)。
- **リスク**: 酸素モデルの近似度がPHA相対誤差1%基準に影響する可能性があるため、両方式の比較測定が必須。

### 優先度5(長期課題): 状態更新のGPU offload

バイオマス更新・PHB/PHV蓄積等の単純な数値更新をCuPy配列演算としてGPU側へ移す。
共有培地更新や条件分岐の多いpH計算はCPU側に残さざるを得ない。

- **期待効果**: 大(環境数が多いほど効く)。
- **難易度**: 非常に高い。大規模リファクタリングと精度監査の再設計が必要。

## 4. 推奨する進め方

1. **優先度4(酸素近似の切替)を最初に試す** — 既存オプションの切替だけで着手でき、コストが最小。
2. 並行して**優先度1(後段CPU並列化)**を実装し、後段CPU完了待ちがどれだけ減るか実測する。
3. それでもGPU待ちが支配的なら**優先度2(ステップ間オーバーラップ)**の本格実装に進む。
4. **優先度3(認証スキップ)**は低コストなので優先度1と並行して試してよい。
5. **優先度5**は長期課題として保留。

いずれの提案も、着手前に既存の「陽性判定基準」(PHA相対誤差1%以下等)への影響を
必ず計測し、速度と精度の両方を報告すること。
