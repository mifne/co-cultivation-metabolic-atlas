# GPU加速dFBA/LPソルバー開発 — 統合開発記録

本ドキュメントは、OR16・NS21（PHB/PHV修正済み）・P. freudenreichiiの3種コミュニティdFBAにおけるGPU優先ハイブリッドLPソルバーの開発過程を4件の原文書から統合したものである。実装は検証付きGPU基底辞書 + CPU再最適化のハイブリッド方式であり、「全LPをGPUで解く」方式ではない。固定32環境×2ステップの独立検証で約6%のCPU時間短縮を確認したが、8ステップ以上・120ステップ・実RL全体での一貫した優位性は未達である。本稿はあくまで開発過程の記録であり、学習済み制御器の性能や実培養での妥当性を示すものではない。各数値・結論は原文に従い転記し、元ファイル間で食い違う場合には注記を付す。

## 1. 初期マイクロバッチ実験

**(出典: `GPU_MICROBATCH_PROGRESS_20260904.md`, 2026-09-04)**

### 1.1 結論と対象

旧来の逐次CPUに対する限定的な高速化は確認済みだが、**4並列CPUに対して安定して高速な実装は未達成**。完全GPU常駐の環境でもない。失敗した計算の所要時間は高速化率に含めていない。

「1ステップ」は培養時間0.2 h分の状態更新であり、PPOの10万ステップ学習全体ではない。

### 1.2 実測（すべて秒、初回準備を除く反復）

| 比較条件 | CPU | GPU | CPU時間/GPU時間 | 結果 |
|---|---:|---:|---:|---|
| 2環境×1ステップ、逐次CPU、既報の1反復 | 2.415 | 0.947 | 2.550 | 精度合格。ただし並列CPUとの比較ではない |
| 8環境×1ステップ、4並列CPU、GPU一律64反復枠 | 3.478 / 3.382 | 4.575 / 4.516 | 0.760 / 0.749 | 全環境合格、GPUは遅い |
| 8環境×1ステップ、4並列CPU、多段修正 | 3.505 / 3.514 | 3.828 / 3.915 | 0.916 / 0.898 | 全環境合格、GPUは遅い |
| 16環境×1ステップ、4並列CPU、多段＋有効部分の行列演算 | 6.773 | 7.552 | 0.897 | 全環境合格、GPUは遅い |

反復数が少なく、信頼区間や有意差は主張しない。初回GPU時間は上表より長い。16環境の初回はCPU 6.945 s、GPU 8.479 sだった。

### 1.3 公平性・精度

- CPUは従来の3段LP目的関数を維持。HiGHS dual simplex、LPごとにthreads=1、parallel=False。4ワーカーにLP配列だけを渡し、COBRAオブジェクトはスレッド共有しない。
- GPUは同じ3段LPと、既存の最適解選択用4段目を使用。CPUの目的関数は変更していない。
- LP組立、転送、ホスト側振り分け、GPU修正、状態更新をオンライン時間に含める。辞書構築・読み込み、環境複製は別枠。初回オンラインのグラフ構築は時間に含む。
- GPU区間ではCPU最適化呼び出しを禁止し、CPU LP呼び出し0を確認した。
- 元LPの主残差≤1e-5、双対残差≤1e-7、相対数値KKT gap≤1e-7。PHA相対誤差≤1%、菌体量絶対誤差≤0.01 g/L、PHV比率絶対誤差≤0.01。
- 16環境の1ステップでは、PHA相対誤差最大3.85e-13、菌体量最大1.36e-13 g/L、PHV比率最大6.74e-13。これはCPU数値解との一致であり、実験精度の保証ではない。

### 1.4 実装変更

1. 独立環境を次のLP呼び出しまで進め、同じ段のLPをGPUにまとめて投入。
2. 基底辞書で認証→小さなGPU修正→不合格行だけ大きなGPU修正。
3. 4段目はまず反復なしで元LPの証明条件を検査し、必要時だけ追加反復。
4. CUDAグラフのキャッシュ不足を修正し、繰り返し再構築を削減。
5. GPU上のカウンターで有効な基底更新数を追跡し、未使用の厳密な単位行列部分を消去計算から除外。
6. 2段目が辞書から修正できないとき、直前の1段目の実行可能な基底から再最適化。

### 1.5 残るボトルネック

8環境×2ステップでは、1ステップ目は全件完了するが、2ステップ目の2段LPで6環境が最適性基準に達しない。1段目基底からの再最適化によって主残差は約1e-12に改善したが、64反復後も双対残差とgapが大きく、不合格として停止した。これを2ステップ完了や高速化とは報告しない。

高速化試験用の基底バンクは元々各段4基底であり、過去の32,768件のsurrogate辞書とは別のもの。追加の独立訓練seed 20286501–20286504で2段LP基底を構築し、網羅性を改善する。検証seed 20286411以降のLPを追加学習に流用しない。

### 1.6 辞書拡張後の確認結果

独立訓練4 seed×2ステップで8個の追加基底を作成し、2段目を4→12基底に拡張した。費用はCPU LP 24回、準備・訓練18.63 s、因数分解52.15 s、計70.78 s。これは事前計算であり、オンラインCPUフォールバックではない。

`pf_gpu_microbatch8_cpu4_extended_step2_20260904.json` では、2ステップ目の2段LPは直接辞書認証3件、GPU修正を含めると6/8件が合格し、不合格が6→2件へ減った。残り2件は最適性に達せず、全環境を1ステップ完了時点で停止している。「6環境が2ステップ完了」とは解釈しない。CPU 7.290 sは全2ステップ分、GPU 8.779 sは失敗までの時間なので、両者から高速化率を算出しない。

辞書を増やすだけでも効果はあるが、全基底を毎回調べるコストも増える。次は訓練分布の追加と基底選択の高速化をセットで行う。

## 2. 検証付きGPU基底辞書とCPU再最適化 — 方法論と開発結果

**(出典: `GPU_HYBRID_METHODS_20260904.md`, 2026-09-04)**

### 2.1 結論と対象範囲

現方式は、事前計算したLP基底からGPU上で候補解を復元し、元LPの制約・最適性を数値検証して採用する。未合格の問題だけを、計算予算を限定したGPU補正またはCPU HiGHSへ送る。CPUへ送る場合もGPUが選んだ基底を初期値として利用できる。したがって「全LPをGPUで解く方式」ではなく、正しさを検証するGPU優先ハイブリッド方式である。

実装は `src/gpu_hybrid_lp.py` の再利用可能なバックエンドとして追加し、`scripts/benchmark_compact_gpu.py` で実際のcommunity dFBAへ接続して検証した。学習エントリポイントの既定経路をこの方式へ切り替えたわけではない。

32環境×2時間ステップの開発用比較では、同じ辞書で初期化するpersistent CPU基準との時間比（CPU/ハイブリッド）が1.031、1.118となった。その後、設定を固定した非重複seed群の5組のgraph再利用条件で、時間比の幾何平均1.0632、対応対数比のt法95%信頼区間1.0182–1.1102を得た（第2.6節）。

これは短時間遷移・32並列という限定条件の結果である。n=5のt区間は対数比の独立性・概ね正規的な分布を仮定し、補助的な両側符号検定はp=0.0625。一般的な速度優越性や120ステップでの持続性は未確認。採用した開発用・独立検証条件はいずれもGPU補正ラウンド0で、独立warm検証のLPの61.875%はCPUへ戻っている。

後続の大辞書・環境別4候補バッチによる32環境×8ステップ比較は、CPU/ハイブリッド比1.0527と0.9809で、精度は両組合格したが速度は正負に分かれた。8ステップでの一貫した優越性は未達である。

### 2.2 計算対象と時間依存性

各環境では、培地・菌体量等からLPを構築し、maxmin、aggregate、exchangeの元の3段階目的を順番に解き、得られた交換・増殖フラックスで状態を更新する。1ステップは0.2時間、今回の2ステップは各環境の培養0.4時間に相当する。時間方向には前後の状態依存があり、独立して並列化する単位は環境群である。

FBAでは同じ最適目的値を与える内部フラックスが複数存在する。交換フラックスまで非一意なら次時刻の状態が変わるため、CPU/GPUの比較では目的の優先順位と許容差をそろえる。3段階目的だけで全交換フラックスの数学的一意性が保証されるとは主張せず、培養軌跡と終点を追加検証する。

### 2.3 実装アーキテクチャ

| 処理 | 現在の役割 | 正確性・性能上の注意 |
|---|---|---|
| オフライン基底辞書 | 学習用LPの基底・写像・入力特徴を保存する。モデルfingerprintと入力族を管理する | ニューラルネットのオンライン学習ではない。評価中のCPU解は辞書へ追加しない |
| 候補の選択と復元 | 現在のLP入力に対し近傍候補等を並べ、compact写像で候補解をGPU上に復元する | 候補の近さは正しさの証明ではない。基底が許す範囲を外れた候補を採用しない |
| cohort一括検証 | 共通候補集合を環境群に適用し、候補復元・証明・選択・分散集計を単一CUDA graphとして再実行する | 候補別host dispatchを減らす。行列演算量そのものが消えるわけではない |
| 元LPの証明 | 主実行可能性、双対実行可能性、相補性に基づく相対KKT gapを検査する | 圧縮空間だけでなく元の全LPを検査。浮動小数点許容差内の証明であり厳密有理数証明ではない |
| 限定GPU補正 | 未合格で低分散の候補について探索方向を制限し、予算内で補正する任意機能 | 補正後も同じ元LP基準を要求。今回の採用開発条件・固定独立検証では無効 |
| CPU fallback | 高分散・分散不明、またはGPU補正予算終了後の未合格問題をpersistent HiGHSで再最適化する | GPU候補基底は初期値にすぎず、HiGHSの最適終了と元LP証明の両方を要求する |
| 状態更新 | 合格したフラックスを用いてhost側dFBAを進める | LP入力組立、経路振り分け、CPU補正、状態更新はGPU内完結ではない |

GPU/CPUで共通の採用基準：元座標の主残差最大値 ≤ `1e-5`、双対違反 ≤ `1e-7`、相対KKT gap ≤ `1e-7`。目的値だけの一致では採用しない。有限値、入力族、モデルの対応も確認する。

主要実装ファイル：`src/gpu_compact_basis.py`、`src/gpu_hybrid_lp.py`、`src/gpu_restricted_basis.py`、`src/cpu_repeated_lp.py`、`src/cpu_dictionary_lp.py`。

### 2.4 分散による振り分けと限界

観測射影は、種別増殖速度、種別交換フラックス、PHA/PHB/PHV関連反応速度で構成し、内部循環フラックスと絶対値用補助変数を除く。候補間の各成分の標本標準偏差を明示的な尺度で割り、最大成分を分散指標とする。現実装の尺度は各成分1であり、実験データから校正した誤差確率や物理的不確実性ではない。

振り分け順序：
1. 元LP証明に合格した候補を優先して採用する。高分散でも合格をCPUへ戻さない。
2. 未合格で、候補数不足または分散非有限なら「分散不明」としてCPUへ送る。
3. 未合格で分散が閾値を超える場合はCPUへ送る。低分散なら任意の短いGPU補正を試す。
4. GPU予算後も未合格なら、低分散でもCPUへ送る。

分散が大きくても複数候補が同じ最適面の正しい解である場合があり、逆に候補が一致していても全候補が誤る場合がある。このため分散は補正の難しさを調べる特徴であり、採用ゲートではない。

現在の閾値は実験的ルールであり、残差減少率・候補数・転送費用を含むGPU/CPU所要時間予測器は未学習である。

現時点の限定的な貢献候補は「同じモデル・階層目的の下で、GPU基底辞書の元LP証明、cohort graph、観測分散に基づく計算先の選択、CPU初期基底への引継ぎを統合し、学習用と評価用を分離してdFBA全体を比較する」ことである。各構成要素は既存研究にあり、新しいLP理論、世界初、一般的なGPU優越性は主張しない。

### 2.7 多GPU化の設計案と未達事項

第一候補は環境群・seed・agentをGPUごとに分ける独立shard方式。各GPUに辞書と担当環境のバッファを持たせ、環境の時系列は同じshard内で進める。CPU fallbackは共通の上限付きworker poolで管理。VRAMが自動的に共有される方式ではなく、3基で3倍になる保証もない。

1個の巨大LPを複数GPUへ分割するPDLP研究は、行列分割と反復ごとの通信を必要とする。小規模LPでは通信費用により遅くなる結果も報告されており、本系ではまず独立環境shardが適切と考える。多GPU実測は未実施。

達成範囲と未達事項の区別：
- 完全GPU内完結：host状態更新とCPU fallbackが残るため未達。
- 5組の非重複seed群・固定32×2条件の確認：完了。対応対数比のt区間は1を上回ったが、小標本の仮定付き結果。別日・別動作点での頑健性は未確認。
- 120ステップ（24時間培養）での精度・速度・メモリ安定性：未確認。
- 強化学習全体の短縮、収束性、総学習時間：この2ステップdFBA比較から外挿しない。
- 分散閾値の校正と有効性：GPU補正を有効化した条件とのablationが必要。
- 多GPUスケーリングと新ワークステーション性能：未測定。

## 5. 総合結論と未達事項

### 5.1 達成範囲

1. **検証付きGPU優先ハイブリッドの実装**: GPU基底辞書→cohort一括証明→CPU fallbackのパイプラインを実装し、精度を維持したまま動作することを確認。
2. **固定32環境×2ステップの独立検証で~6%短縮**: 5組warmの時間比幾何平均1.063、対応t区間[1.018, 1.110]（p=0.0625の符号検定）。ただし小標本・限定的な条件。
3. **同値なhost最適化**: 固定配列入力パス、選択特徴量抽出により、CPU・GPU両方のLP準備時間を削減。
4. **非同期パイプライン**: CPU LPとhost状態更新の重ね合わせにより、hybridの一貫した改善（4.66–15.08%）を確認。

### 5.2 未達・未検証

- **完全GPU内完結**: host状態更新・CPU fallbackが残り、`n`GPUのみでの解決は未達。
- **8ステップ以上の一貫した優越性**: 32x8、大辞書K=4で正負に分かれた結果。一貫した優位性なし。
- **120ステップ（24時間培養）での優位性**: むしろhybridが6.25%遅い結果。
- **強化学習全体の高速化**: 2ステップdFBAの結果から外挿不可。
- **多GPUスケーリング**: 実測未実施。
- **GPU補正の有効化**: 準備費用が高く、現状では既定化に至らず。
- **RNN/GRUによる時系列warm-start**: 学習・補正接続は試作段階で、合格解0件・CPUより低速。
- **等式保存型縮約+GPU PDHG**: 反復速度改善（1.8倍）は確認したが、元LP合格0件のためFBA throughputとして無効。

### 5.3 最終開発優先順位（変更なし）

1. 改善：中盤（step 41–60）のaggregate/exchange候補被覆・選択を新規学習軌跡から改善。
2. 改善：host状態更新の配列中心設計と固定superpattern exchange更新。
3. 改善：GPU補正の費用対効果を測定し、集合的なbatch処理で準備費用を償却。
4. 検証：8ステップで一貫した改善を確認後、120ステップ→実RLへ段階的に進む。
